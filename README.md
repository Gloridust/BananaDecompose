# BananaDecompose

用 **Nano Banana 2**（`google/gemini-3.1-flash-image`，走 OpenRouter）生成图像，并把它变成**可编辑的图层 + 真实可改的文字**。

**中间是一张节点画布。** 每条方案分支的每个中间产物 —— 规划、背景板、每张原始底片、每次抠图、最终成品 —— 都是画布上的一个节点，边指向它的来源。共享的上游只画一次，所以「为什么这个对比是公平的」是画出来的，不是写在文档里的。

一次生成 = 一张画布 = 一条历史记录。

两条管线：

| | A · 生成即分层 | B · 事后拆解 |
|---|---|---|
| 思路 | 先规划结构，元素逐个独立渲染，文字全程不进像素 | 先出一张拍平的成品，再把它拆回图层 |
| 可编辑性 | **设计出来的** —— 文字是真文本节点，图层天生独立 | **抢救出来的** —— 文字靠 OCR，图层靠分割 + 重绘补洞 |
| 精度上限 | 无损（元素本来就没合过） | 约 PSNR 26 / LPIPS 0.09，视觉可用但非像素级 |
| 能处理外来图 | ❌ 只能编辑本系统生成的 | ✅ 可以上传任意平图 |
| 依赖 | 纯 API | 纯 API |

**为什么两条都做**：A 是正确答案，B 是唯一能处理"别人给的一张图"的路。把它们放进同一个对比框里，差距是能被量化出来的，而不是靠嘴说。

## 快速开始

```bash
npm install
cp .env.local.example .env.local   # 填入 OPENROUTER_API_KEY
npm run dev
```

打开 http://localhost:3000 。

不填 key 也可以打开 **http://localhost:3000/selftest** —— 自检页，验证抠图数学（用已知 alpha 的合成图）和节点画布布局（用一张合成的三分支画布），不消耗任何 API。

## 部署到 Vercel

直接 import 仓库即可。唯一必须配的环境变量是 `OPENROUTER_API_KEY`。

架构上专门为 serverless 做了让步：**每个 API route 只做一次模型调用**，多步编排全部放在浏览器里。所以没有任何一个函数会逼近 Vercel Hobby 的 60s 上限，也不需要队列或后端状态。

## 关键设计决策

### 1. Nano Banana 不输出 alpha —— 这是绕不开的硬约束

Gemini 系图像模型（Nano Banana / Pro / 2）**全都只输出不带 alpha 通道的 RGB**。要求"透明背景"，拿到的是纯白、纯黑，或者画上去的马赛克格子。

所以透明是**算出来的**，四种策略在 UI 里可切：

| 策略 | 做法 | 成本 | 自检实测 |
|---|---|---|---|
| **双渲染差值** | 白底 + 黑底各生成一次，解 `α = 1 − (C_white − C_black)`，`色值 = C_black / α` | 2× | 平均 alpha 误差 **0.10%** |
| 色键抠图 | 在纯品红底上生成一次，按色距抠除 + 去色溢 | 1× | 平均 alpha 误差 **4.17%**，软边有明显品红边 |
| VLM 分割掩码 | 灰底生成一次 + Gemini 返回 segmentation mask | 1× + 1 视觉调用 | 取决于 grounding 质量 |

（`background=transparent` 那条路没做 —— Gemini 全系不支持，留一个必然失败的选项只会浪费用户的钱。）

数字来自 `/selftest`：真值是带羽化边缘的圆盘 + 45% 半透明横条，专挑软边和半透明两种最难的情况。**注意这是算法上限** —— 自检里两张底片像素级一致，真实模型两次生成会有漂移，实际误差更大。

所有像素运算都在浏览器 canvas 里跑（`lib/matte.ts`），服务端不碰图像数据。

### 2. 文字永远不烘焙进像素

管线 A 的核心。规划阶段就把文案单独拎出来，出图 prompt 里明确要求"不要画任何文字、给文字留白"，最终文字用真实 DOM 文本节点渲染。

结果：改字、换字体、换语言全都是零损耗的，导出的 SVG 里文字是 `<text>` 节点而不是描边路径。**这是整个 demo 的验收标准。**

对照组 `文字策略 = 烘焙后回收` 会走完整的 OCR → 擦除 → 重排流程，用来量化"事后回收"到底掉多少精度。

### 3. 模型分三个槽

| 槽 | 默认 | 干什么 |
|---|---|---|
| `OPENROUTER_IMAGE_MODEL` | `google/gemini-3.1-flash-image` | 出图、编辑、擦除重绘 |
| `OPENROUTER_VISION_MODEL` | `google/gemini-3.7-flash` | 规划 Scene JSON、读版面、OCR |
| `OPENROUTER_GROUNDING_MODEL` | `google/gemini-3.1-pro-preview` | box_2d + segmentation mask |

grounding 单独一个槽是有原因的：**3.x Pro 线明确文档化了 `box_2d` + segmentation mask 输出，Flash 线没有。** 而管线 B 的拆解精度几乎全押在这上面。规划和 OCR 这些活儿用 3.7 Flash（$0.75/$3.75，正式版）比 3.1 Pro（$2/$12，还挂 preview）划算得多，但掩码这一步值不值那点钱，切一下对比就知道。两个槽都能在 UI 里按次覆盖。

### 4. 节点画布

画布上的节点类型：

| 节点 | 内容 | 是否共享 |
|---|---|---|
| 提示词 | 一切的根 | 全局唯一 |
| 规划 | Scene JSON：元素列表 + 文案 | A 组共享 |
| 背景板 | 全幅背景 | A 组中文字不入像素的分支共享 |
| 来源图 | 拆解管线的起点平图 | B 组共享 |
| 读版面 | 从像素里读回的元素 + 文字 | 每分支独立 |
| 渲染 | 每个元素的原始底片（白/黑/品红/灰底） | 每分支独立 |
| 抠图 | 抠完的 RGBA 元素 | 每分支独立 |
| 重绘 | 擦除后重建的背景板 | 每分支独立 |
| 成品场景 | 组装好的可编辑结果 | 每分支独立 |

**开关**：顶部每条分支有开/关和「只看这一条」；节点右上角的 ✕ 单独隐藏某个节点。关掉分支时，只被它用到的节点连同边一起消失，共享节点因为还有别的分支在用而留下 —— 这个行为本身就说明了哪些东西是共用的。

滚轮缩放（以光标为锚点）、拖空白处平移、右下角「适应画布」。

点**成品场景**节点打开图层编辑器浮层：拖拽、缩放、双击直接改字、改字体颜色、导出 PNG / SVG / JSON。可编辑图层和真实文字始终是这个 demo 的立身之本 —— 画布负责展示「怎么来的」，编辑器负责证明「真的能改」。

### 5. 一键评测：变量必须只有一个

左栏底部的**一键评测**把七种方案用同一条提示词挨个跑一遍，全部落到同一张画布上。

关键在于**同管线的各组共享上游产物**：

- A 组共享同一份 Scene 规划，也共享同一张背景板（抠图策略压根不影响背景）
- B 组共享同一张来源平图
- 只有「文字烘焙回收」那组会自己重新生成背景 —— 因为它的背景里必须有字

不这么做的话，所谓"评测"就只是七次互不相干的生成摆在一起，差异里混着模型的随机性，什么也说明不了。共享上游顺带把出图次数从 32 降到 30。

在画布上，这件事表现为**一个规划节点扇出到七条链路**，标着「共享 ×7」。

### 6. 文字：粗定位靠模型，精定位靠像素

拆解管线最难看的地方是文字对不准。根因是 Gemini 的 `box_2d` 精度不够 —— [Google 自己的文档](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/bounding-box-detection)就写明它是"不用训练自定义模型的通用检测"，并承认 fine-level coordinate precision 不足。模型报的 `fontSize` 更是纯猜。

所以职责拆开：**模型说这是什么字、像什么字体；像素说它在哪、多大、什么颜色。**

流程（`lib/glyph.ts` + `lib/pipeline/text.ts`）：

1. **去重** —— 版面识别很容易把同一处读成两条 run（「V60杯」和「V60」），两层叠在一起就是双影
2. **量墨迹** —— 粗框外扩 20%，取裁片边缘环的中位数当局部底色，按色距построить距离场，Otsu 自动分割。得到精确 bbox、精确颜色（笔画核心像素中位数）、带软 alpha 的字形抠图
3. **裁图复核**（可关）—— 把字形裁出来放大送回视觉模型，重新确认内容和字体。**只问内容和样式，不问几何** —— 几何是量出来的
4. **字体回测** —— 先按高度缩放、让宽度自由分歧，用「自然宽度契合度 × 0.6 + 轮廓 IoU × 0.4」打分。分差不足 0.06 时判定为不可分辨，交回模型的判断
5. **二参拟合** —— 解出字号和字距，让渲染墨迹框严格等于量出的墨迹框

`/selftest` 用已知真值验证（带纹理的底 + 故意画歪的粗框）：**位置偏差 <1px，颜色完全一致，字体 3/3 正确**。

> 自检逮住过两个真 bug：一是早期版本用字距强行把宽度拉齐，把字体最强的区分信号抹掉了（字体回测 0/3、字号误差 7%）；二是**冷加载时 web 字体根本还没被请求** —— `document.fonts.ready` 只等已发起的请求，而 Google Fonts 的字体要等到真正渲染匹配字形才会去取。测量拿到的是 fallback 的度量，所有候选看起来一模一样，表现为"字体分不出来"而不是报错。现在测量前会显式 `document.fonts.load()` 每个候选（带样本文字，因为 CJK 字体是分子集下发的）。

### 7. 文字放回：重排 vs 保留原始笔画

量准了位置之后还有一个取舍：

| | 重排为真文本 | 保留原始笔画 |
|---|---|---|
| 做法 | 用量出的字号/位置/颜色在 web 字体里重排 | 用量出的掩码把原字抠成 RGBA 图层 |
| 保真 | AI 画的笔画还原不了 | **像素级一致** |
| 改字 | 直接改，零成本 | 交给 Nano Banana **按原样式重绘**（2 次调用） |

保留原始笔画是默认。改字时把原字裁片作为 style reference 回传给 Nano Banana，让新词沿用同一只手 —— 这才是手写体、艺术字、AI 生造字形唯一还能编辑的方式。选中该图层后在属性面板里改字重绘。

### 8. 背景只在需要的地方合成

`erase` 是整图重绘，输出会全局漂移。所以只在**真正抬走东西的地方**采用重绘像素：

```
去文字图 = 原图 × (1−文字掩码) + 重绘图 × 文字掩码
背景板   = 去文字图 × (1−元素掩码) + 重绘图 × 元素掩码
```

其余像素与原图逐位一致。而且元素是从**去文字图**上切的 —— 这样抬起一个元素时不可能把烘焙的文字一起带到干净底板上，这正是之前双影的来源。

没拿到掩码的元素**不生成图层**，留在背景里。往干净底板上贴一个带原文字的矩形是纯负收益。

**背景重建没有开关，一定会做。** 底板上还留着已经被抬走的东西，那不是分层文件，只是一张图上面浮着它自己的副本 —— 起不到产品级的分层作用。所以：

- 擦除区域**永远存在**：量到墨迹就用精确框，没量到就退回模型给的粗框。擦大一点无所谓，反正那块要重建；漏擦一段就等于在图层底下留了一个自己的副本。
- 之前那两条产出脏背景的评测分支（`掩码关` / `全关`）已经删掉了。它们展示的不是取舍，是不可用。
- 只有重建被模型拒绝时才会留脏背景，那是运行时故障，成品场景节点会用黄色标出来。

### 9. 并发：全局调度器 + 共享上游提前跑

原来的结构有个隐藏的串行瓶颈：共享的规划/背景板/来源图是**第一条分支跑出来的副产品**，所以后面每条分支都得等它整条跑完。七条分支实际是一条接一条。

现在拆成两阶段：

```
阶段 0（共享上游，两条管线互不依赖，并行）
  规划 ──→ 背景板          ┐
  来源图                    ┘

阶段 1（全部分支同时开跑）
  ├─ A·双渲染   ─────────┐
  ├─ A·色键     ─────────┤
  ├─ A·VLM掩码  ─────────┼──→ 各自的成品场景
  ├─ A·文字烘焙 ─────────┤
  ├─ B·掩码+重绘 ────────┤
  ├─ B·仅重绘   ─────────┤
  └─ B·全关     ─────────┘
```

节流从「每条分支各限 2 路」改成**一个全局调度器**：所有分支共用一个在飞请求池，上限在左栏可调（默认 4）。这样分支数量不再乘进请求量 —— 加分支只会排队，不会打爆限流。

顶栏运行时实时显示 `在飞 3/4 · 排队 7`。

### 10. 每条路径的耗时

- **成品场景节点上直接标 `⏱ 48.3s`** —— 这条路径从分支开始到成品的墙钟耗时，这就是你要横向比的数
- 分支开关上带一个小的秒数
- 顶栏右侧：`墙钟 118.4s / 串行 312s · 省 62%` —— 并发到底省了多少，不用你自己算

### 11. 自动量化指标

每次运行结束后从已有像素里算出来，不额外花钱：

| 指标 | 含义 | 适用范围 |
|---|---|---|
| **软边占比** ↑ | 存活像素里半透明的比例。羽化边被正确还原时不该是 0 —— 硬阈值抠图会把它压平 | 全部 |
| **存活面积** | 抠完剩下多少画面，太低说明主体被啃掉了 | 全部 |
| **底色残留** ↓ | 仍贴近键色的像素比例 | 仅彩色底（色键 / 灰底）。双渲染没有单一键色，报 `—` |
| **重建 PSNR / L1** | 图层叠回去和原图的差距 | 仅拆解管线 —— 只有它有原图可比 |
| 文字来源 | 「未入像素」还是「OCR 回收」 | 全部 |

对比表里每行最优值标绿。`—` 是"不适用"，不是"没测出来"。

### 12. 历史记录：localStorage 索引 + IndexedDB 数据

画布的**索引**存 localStorage（列表秒开、devtools 里可读），**节点数据**存 IndexedDB。因为节点图像是 data URI，localStorage 那 ~5MB 配额大概只装得下两张生成图，而这个 demo 的意义就是攒很多张画布来对比。

`/history` 列出所有画布，展开任意一张看它的分支缩略图、完整指标表，以及这张画布上有哪些节点是被共享的。点「在画布打开」回到工作台继续编辑。

```
lib/board.ts       分层 DAG 布局：深度分列、分支分道、共享节点居中
lib/pipeline/scheduler.ts  全局请求调度器：所有分支共用一个在飞池

lib/retype.ts      保留原始笔画的图层改字：按原样式重绘 + 双渲染抠图
lib/prompts.ts     所有 prompt 模板与 JSON schema
lib/pipeline/      两条管线的编排（跑在浏览器，逐步上报进度和成本）
lib/export.ts      导出 PNG / SVG(文字为 <text>) / Scene JSON
lib/history.ts     localStorage 索引 + IndexedDB 存储

components/Board.tsx        节点画布：平移缩放、贝塞尔连线、节点/分支开关
components/SceneEditor.tsx  图层编辑器浮层（点成品场景节点打开）
components/Stage.tsx        DOM 图层渲染：拖拽、缩放、双击直接改字
app/selftest                自检：抠图数学 + 画布布局，不消耗 API
```

## 这套方案参考了什么

事后拆解那条线（管线 B）基本是 **ReDesign**（2026）的形状，去掉本地 GPU：VLM 当控制器读版面，原生 grounding 出掩码，图像模型顶替本地 LaMa 做补洞。

值得知道的相关工作：

- [**Qwen-Image-Layered**](https://github.com/QwenLM/Qwen-Image-Layered) — Apache 2.0，ComfyUI 原生支持，端到端拆成多张 RGBA 图层，支持变层数和递归再拆。目前**最强的开源可落地拆解方案**，但要 GPU（1024px 约 120s，峰值 45GB），所以没做进这个纯 API demo。
- [**ReDesign**](https://arxiv.org/html/2607.25565) — agentic 分解树，VLM 控制器在五个 action 间递归选择，每步有 verifier 判 accept / prune / retry。
- [**OmniPSD**](https://arxiv.org/pdf/2512.09247) — 文字层恢复：OCR → 字体嵌入检索 → 矢量重渲染，产出真·可编辑 PSD 文本对象。
- [**LayerD**](https://www.emergentmind.com/topics/layerd) / [**LiWi**](https://arxiv.org/html/2605.14552) / [**LaDe**](https://arxiv.org/pdf/2603.17965) — 自然图像分层的学术 SOTA。

## 已知边界

- **双渲染差值靠模型两次生成的一致性。** 主体漂移会直接变成 alpha 噪点。Nano Banana 的跨次一致性够好，但不是保证。
- **字体回测是弱识别器。** 自然宽度 + 轮廓 IoU 在自检的三组里全对，但它比不了训练过的字体识别模型（Adobe 那套背后是 3 万+ Adobe Fonts 的检索）。分差不足时会主动认怂、交回模型判断。想要更准就得接 WhatFontIs 一类的服务 —— 或者干脆用「保留原始笔画」，那样根本不需要认字体。
- **Adobe 把这个功能砍过。** Illustrator/Photoshop 的 Retype 曾经能把图里的静态文字转成可编辑文本层，[现在只保留字体识别](https://bringyourownlaptop.com/blog/how-to-use-retype-in-illustrator)，转换功能已移除。这是这条路难度的一个强信号。
- **`erase` 是整图重绘**，模型可能顺手改动本该不变的区域。生产环境应该配掩码做局部重绘。
- **`erase` 会被版权过滤器拦。** 对着含艺术字的图片要求"移除文字"，Gemini 有时会返回 `flagged for copyrighted or trademarked material`。提示词已经改成「把表面恢复成空白状态」这种修复式表述来降低触发率，被拒时该步骤降级为沿用原图（节点标黄、注明"重建被拒"），而不是让整条分支归零。
- **掩码是一次一个对象请求的。** 掩码以 base64 文本形式混在补全流里返回，一次要多个会把输出推到几万 token —— 实测超过 170s 还没返回。现在的做法是把输入图降到 768px、每个对象单独一次调用、45s 超时后干净降级成矩形裁切（步骤日志里会标注）。即便如此，grounding 仍是整条管线里最慢也最容易失败的一步。
- **成本估算是粗的**（按 1K 图 $0.08/张），只算出图不算视觉调用。真实数字以每条运行记录为准。
- **z-order 是模型推断的**，没有深度估计兜底（那需要 Depth Anything 一类的本地模型）。
