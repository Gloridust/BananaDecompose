# 文字回收

拆解管线最难看的地方是文字对不准。这份文档讲根因和解法。

## 根因

Gemini 的 `box_2d` 精度不够。[Google 自己的文档](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/bounding-box-detection)写明它的定位是"不用训练自定义模型的通用检测"，并承认 fine-level coordinate precision 不足、偶有漏检和幻觉。模型报的 `fontSize` 更是纯猜。

**Google 自己把职责分得很清楚**：Gemini 负责读和推理，精确几何用 Cloud Vision 的 `DOCUMENT_TEXT_DETECTION`（返回逐字符 vertices）。

本项目坚持纯 Gemini，所以走另一条：

> **模型说这是什么字、像什么字体；像素说它在哪、多大、什么颜色。**

## 流程

`lib/glyph.ts` + `lib/pipeline/text.ts`

### 1. 去重

版面识别很容易把同一处读成两条 run —— 实测「V60杯」和「V60」会同时出现在同一个标注上。两层叠在一起就是双影。

按 IoU > 0.45 合并，保留转写更长的那条（更完整的读法）。

### 2. 量墨迹

```
粗框外扩 20%
  → 取裁片边缘环的中位数当局部底色（padding 就是为了这个环落在底上）
  → 逐像素算到底色的距离，构成距离场
  → Otsu 自动阈值分割
```

Otsu 不需要手调阈值，而且**浅底深字和深底浅字走同一条路径**。

产出：

- **精确 bbox** —— 墨迹的紧框
- **精确颜色** —— 笔画核心像素（距离 > 1.5×阈值）的中位数；边缘像素是混色的，不参与
- **带软 alpha 的字形抠图** —— alpha 沿距离场渐变，抗锯齿的笔画边缘得以保留而不是被切成锯齿
- **样式参考裁片** —— 带 padding 的不透明裁片，供后续重绘用

密度低于 0.4% 或高于 75% 判为分割失败，退回模型的框。

### 3. 裁图回传复核（可关）

把字形裁出来放大送回视觉模型，重新确认**内容、字体、字重、是否斜体**。

**只问内容和样式，不问几何。** 裁片里字大了模型看得清，转写和字体判断显著变准；但它在裁片里依然是"回归"一个框，赢不了直接测量墨迹像素。

每段一次便宜调用（Flash 档、几百 input token）。

### 4. 字体回测

把候选字体逐个渲染出来跟量到的墨迹打分：

```
score = 自然宽度契合度 × 0.6 + 轮廓 IoU × 0.4
```

两个信号缺一不可：

- **自然宽度**：先按高度缩放、**让宽度自由分歧**。字体的 advance widths 差异明显，这是最强的单一信号
- **轮廓 IoU**：只在形态学梯度（墨迹的一圈外壳）上算，因为衬线的差异就在轮廓上；填充面积的 IoU 几乎分不出字体

分差不足 0.06 判定为**不可分辨**，交回模型的判断。渲染回测是弱识别器，跟训练过的字体识别模型（Adobe 背后是 3 万+ Adobe Fonts 的检索）没法比，所以它必须会认怂。

### 5. 二参拟合

解出字号和字距，让渲染墨迹尽量贴合量出的墨迹，**但绝不溢出**：

```
按高缩放 = 探针字号 × 目标墨迹高 / 探针墨迹高
按宽缩放 = 探针字号 × 目标墨迹宽 / 探针墨迹宽
字号     = min(按高, 按宽)                     ← contain，不溢出
字距     = (目标墨迹宽 − 该字号下的墨迹宽) / 字符间隙数
```

**取两者较小值**是关键。只按高度缩放，遇到书法体/美术字就会炸：原字字面窄、笔画粗，按它的墨迹高去缩放常规字体，四个方块字的自然宽度可能是目标的 1.6 倍，负字距撞到下限也拉不回来。实测「晨间萃取」溢出 40%，整个标题糊成一团。

代价是替换字体会比原字**矮**。这是诚实的取舍：溢出会盖住旁边的东西，矮一点不会。差异超过 25% 时会写进 `provenance`（"原字比替换字体窄 N%，多半是书法/美术字"）。填不满的空间做居中，而不是靠左上角。

然后按字体自身的 bearing 反推图层框的原点。

**匹配墨迹框而不是基线/cap height，彻底绕开了西文和中日韩的排版语义差异** —— 两边都由"像素实际在哪"定义。

## 自检实测

`/selftest` 用**已知字号/位置/颜色的文字渲染到带纹理的底上**，再喂给引擎一个**故意画歪的粗框**（模拟 VLM 的 box_2d）：

| | 字号真值→量出 | 位置偏差 | 颜色 | 字体 |
|---|---|---|---|---|
| 晨间萃取 | 96 → 96.5 | -0.7, -0.5px | ✅ 完全一致 | Noto Serif SC ✓ |
| 周六 9:00 · 三号仓库 | 46 → 45.9 | -0.3, -0.5px | ✅ 完全一致 | Noto Sans SC ✓ |
| MORNING EXTRACTION | 78 → 79.2 | -0.2, -0.1px | ✅ 完全一致 | Bebas Neue ✓ |

红色的恢复层叠在原图上，完全重合。

> **自检逮住过三个真 bug**，都不是写代码时想得到的：
>
> 0. **只按高度定字号，遇到书法体直接溢出 40%**。现在回归用例用 Bebas Neue（极窄）量、Georgia（宽）拟合：字号从 140 缩到 75.9，溢出 0px。
>
> 1. 早期版本用字距强行把宽度拉齐来对齐 —— 等于把字体最强的区分信号抹掉了。字体回测 0/3、字号误差 7%。
> 2. **冷加载时 web 字体根本还没被请求**。`document.fonts.ready` 只等已发起的请求，而 Google Fonts 的字体要等到真正渲染到匹配字形才会去取。测量拿到的是 fallback 的度量，所有候选看起来一模一样 —— 表现为"字体分不出来"而不是报错。现在测量前会显式 `document.fonts.load()` 每个候选，**并带上样本文字**（CJK 字体是分子集下发的，不给样本就取不到对的子集）。

## 保留原始笔画

量准位置之后还有一个取舍：

| | 重排为真文本 | 保留原始笔画（默认） |
|---|---|---|
| 做法 | 用量出的字号/位置/颜色在 web 字体里重排 | 用量出的掩码把原字抠成 RGBA 图层 |
| 保真 | AI 画的笔画还原不了 | **像素级一致** |
| 改字 | 直接改，零成本 | 交给 Nano Banana 按原样式重绘（2 次调用） |
| 对擦除失败 | 会与残留的原文字重影 | **免疫** —— 抠出的原字正好落回它自己的位置 |

改字时把**原字裁片当 style reference** 回传（`lib/retype.ts`），让新词沿用同一只手，再用双渲染差值抠图。文字几乎全是抗锯齿边缘，硬阈值抠图会让每一笔都发毛，所以这里必须用双渲染。

这是手写体、艺术字、AI 生造字形唯一还能编辑的方式。

## 一个值得看的外部信号
